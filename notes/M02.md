# M02 · Vectors: std::vector, iterators, capacity, reallocation, erase-remove

## Core ideas
```cpp
std::vector<Point3> cloud;            // {ptr, size, capacity}: 24 B on the stack, data on the heap
cloud.reserve(n);                     // capacity >= n, size unchanged, nothing constructed
cloud.resize(n);                      // size = n, new elements value-initialised (zeros)
cloud.push_back({1, 2, 3});           // copy/move in; amortised O(1)
cloud.emplace_back(Point3{1, 2, 3});  // construct in place (aggregates need C++20 for emplace_back(1,2,3))
cloud.clear();                        // size 0, capacity KEPT (reuse per scan)
cloud.shrink_to_fit();                // non-binding request to free the slack
std::vector<Point3>().swap(cloud);    // guaranteed release
```

### erase-remove idiom (stable, O(n))
```cpp
cloud.erase(std::remove_if(cloud.begin(), cloud.end(),
                           [](const Point3& p) { return p.z < -1.5; }),
            cloud.end());
// C++20: std::erase_if(cloud, pred);
```
In-place write index (for filters that depend on the index, like "every Nth"):
```cpp
std::size_t w = 0;
for (std::size_t i = 0; i < v.size(); ++i) if (keep(i, v[i])) v[w++] = v[i];
v.resize(w);
```
Order doesn't matter? Use **swap-and-pop**: `std::swap(v[i], v.back()); v.pop_back();`, which is O(1).

## What happens in memory / cost table
| Operation | Cost | Invalidates |
|---|---|---|
| `v[i]`, `v.at(i)` | O(1). `at` bounds-checks and throws | – |
| `push_back` (no realloc) | O(1) | `end()` only |
| `push_back` (realloc) | O(n) move/copy + malloc/free | **everything** |
| `insert`/`erase` middle | O(n − pos) shift | at/after pos (everything if realloc) |
| `pop_back` | O(1) | the last element, `end()` |
| `reserve(n)` (n > cap) | O(size) | everything |
| `clear()` | O(size) dtors | everything (but capacity stays) |
| `swap(a, b)` | O(1), swaps 3 pointers | iterators follow the elements to the other vector |

Growth: ×2 (libstdc++/libc++) or ×1.5 (MSVC). Geometric growth means total copies < 2n, which gives amortised O(1).
Elements are moved during a reallocation only if the move ctor is **`noexcept`**; otherwise they're copied (strong exception guarantee).

## Pitfalls interviewers ask
1. **Reference/iterator held across `push_back`** gives a dangling pointer after reallocation (ASan: heap-use-after-free).
2. **`erase` in a loop**: `it` is invalidated, and the result is O(n²). Use erase-remove.
3. **`std::remove` alone** doesn't shrink `size()`.
4. **Self-append**: `for (auto& p : v) v.push_back(p);` reallocates mid-loop and never terminates. Use reserve plus an index loop over a saved `n`.
5. **`reserve` then `v[i] = …`** is UB because size is still 0. Use `resize`, or `push_back`.
6. **`v.size() - 1` on empty** wraps to SIZE_MAX.
7. **`vector<bool>`** is a bit proxy: no `bool&`, slow, not thread-safe per element.
8. **`v.data()` of an empty vector** may be nullptr. Don't dereference it.

## Robotics angle
- Keep a scratch `std::vector` member per node and `clear()` it each frame. After warm-up there are zero mallocs.
- Pre-`reserve` from the sensor's known point count (e.g. 64 × 2048 for an OS1-64).
- Store landmarks and keyframes in a vector and refer to them by **index/id**, never by pointer, while the vector grows.
- Struct-of-arrays (`xs, ys, zs`) vs array-of-structs (`vector<Point3>`): SoA vectorizes better, AoS has better per-point locality.
- `std::vector<Eigen::Vector4d>` used to need `Eigen::aligned_allocator` before C++17 (over-aligned types).

## Rapid-fire questions
<details><summary>Show answers</summary>

- *size vs capacity?* size = constructed elements; capacity = allocated slots.
- *Why is push_back amortised O(1)?* Geometric growth: n pushes cause < 2n element moves in total.
- *When does a vector move rather than copy on growth?* When `T`'s move ctor is `noexcept` (`std::move_if_noexcept`).
- *Does `clear()` free memory?* No. Use `shrink_to_fit` or the swap trick.
- *Fastest unordered removal?* Swap with back, then `pop_back`.
- *What does `std::remove_if` return?* An iterator to the new logical end. The tail elements are valid but unspecified.
- *`emplace_back` vs `push_back`?* emplace constructs in place from ctor args. With an existing object they're the same.
- *Is `std::vector` contiguous?* Yes, guaranteed. `data()` gives a C pointer for BLAS/GPU uploads.
</details>

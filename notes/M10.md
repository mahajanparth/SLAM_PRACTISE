# M10 · Memory Management: stack vs heap, new/delete, RAII, alignment

## Core ideas
```cpp
void scanLoop() {
  Point3 p{};                               // stack: automatic, freed at scope exit, ~free
  std::array<float, 1024> ranges{};         // stack: fixed size, careful with big arrays (8 MB default stack)
  std::vector<Point3> cloud(100000);        // object on stack, BUFFER on heap (malloc)
  auto* raw = new Point3{1, 2, 3};          // heap: you must delete it...
  delete raw;                               // ...exactly once, with the matching form
}
```

| Allocate | Free with | Notes |
|---|---|---|
| `new T(args)` | `delete p` | calls ctor / dtor |
| `new T[n]` | `delete[] p` | stores a hidden count for dtors, so a mismatch is UB |
| `std::malloc(bytes)` | `std::free(p)` | no ctors or dtors; returns `void*`; C interop |
| `::operator new(bytes)` + placement `new (buf) T` | `p->~T()` + `::operator delete(buf)` | separate allocation from construction (pools, vector) |
| `std::make_unique<T>(...)` | automatic | **default choice** |

### RAII: Resource Acquisition Is Initialization
Acquire in the constructor and release in the destructor. Destructors run on **every** exit path (return, break, exception), so you get no leaks or double frees, and exception safety comes for free.
```cpp
class LidarHandle {
  c_lidar* h_ = nullptr;
 public:
  explicit LidarHandle(int port) : h_(c_lidar_open(port)) { if (!h_) throw std::runtime_error("open"); }
  ~LidarHandle() { c_lidar_close(h_); }
  LidarHandle(const LidarHandle&) = delete;                    // unique ownership
  LidarHandle(LidarHandle&& o) noexcept : h_(std::exchange(o.h_, nullptr)) {}
};
// Equivalent one-liner:
using LidarPtr = std::unique_ptr<c_lidar, decltype(&c_lidar_close)>;
```
RAII is everywhere in the standard library: `vector`, `string`, `unique_ptr`, `lock_guard`, `fstream`, `thread` (join), and so on.

### Alignment
```cpp
alignof(double) == 8;  sizeof(struct{char c; double d;}) == 16;   // padding
struct alignas(32) Simd8f { float v[8]; };                        // AVX-friendly
std::uintptr_t alignUp(std::uintptr_t n, std::size_t a) { return (n + a - 1) & ~(a - 1); }  // a = 2^k
void* p = std::aligned_alloc(64, 64 * k);  /* size must be a multiple of the alignment */  std::free(p);
```
C++17: `new` honours `alignas` > 16 (aligned `operator new`), so the Eigen `EIGEN_MAKE_ALIGNED_OPERATOR_NEW` dance is unnecessary for C++17 code.

## What happens in memory / cost
| Operation | Cost (order of magnitude) |
|---|---|
| Stack allocation | ~0 (adjust the stack pointer) |
| `malloc`/`new` small block | 20–100 ns, may take a lock or touch a cold cache line |
| `free`/`delete` | similar; fragmentation over long runs |
| Page fault on first touch of a fresh big allocation | ~µs per 4 KB page |
| Pool/arena allocation | a few ns (bump pointer or free-list pop) |
| Reading misaligned data | usually OK on x86 (slower across cache lines); a fault for aligned SIMD loads |

## Pitfalls interviewers ask
1. **`new[]` + `delete`** (or `malloc` + `delete`) is UB.
2. **Leak on an exception path**: a raw `new` before a call that may throw.
3. **Double free / use-after-free** from two raw owners, or an observer outliving its owner.
4. **Returning a pointer or reference to a stack local.**
5. **Rule of three violation**: a class with a raw owning pointer and the default copy ends up double-deleting.
6. **Huge stack arrays**: `float img[4000*3000];` overflows the stack.
7. **`vector` growth invalidates pointers.** Use indices, `deque`, or a pool when addresses must be stable.
8. **Padding** wastes memory and bandwidth: order struct members largest to smallest.

## Robotics angle
- Real-time loops (control at 1 kHz) avoid heap allocation entirely: preallocate, `reserve`, reuse buffers, use pools.
- Map point/landmark pools give stable addresses for graph edges and cut allocator overhead.
- Vendor SDKs (lidar, camera, CAN) are C APIs, so wrap every handle in an RAII class or a `unique_ptr` with a custom deleter.
- Eigen fixed-size vectorizable types and SIMD point buffers need alignment awareness (`aligned_allocator` pre-C++17).
- Long-running vehicles: small leaks become out-of-memory kills after hours. Run ASan/LSan in CI.

## Rapid-fire questions
<details><summary>Show answers</summary>

- *Stack vs heap?* The stack is automatic, LIFO, tiny (MBs) and fast. The heap is dynamic, large, has an explicit or RAII lifetime, and is slower.
- *What is RAII?* Tying a resource's lifetime to an object's lifetime: acquire in the constructor, release in the destructor.
- *Why does RAII give exception safety?* Stack unwinding runs destructors of all fully constructed locals.
- *`new` vs `malloc`?* `new` is type-safe, calls constructors, throws `bad_alloc`, and is replaceable per class. `malloc` returns raw bytes, gives NULL on failure, and calls no constructors.
- *What's placement new?* Constructing an object in memory you already own: `new (buf) T(args)`. You must call `~T()` manually.
- *Why `sizeof(S)` > the sum of its members?* Padding for member alignment, plus tail padding so arrays stay aligned.
- *How do you detect leaks?* ASan/LSan (`-fsanitize=address`), Valgrind, heaptrack.
- *Is a destructor allowed to throw?* It's implicitly `noexcept`, so throwing calls `std::terminate`. Handle errors inside it.
</details>

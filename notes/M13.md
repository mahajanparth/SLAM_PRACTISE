# M13 · Inheritance: base/derived, access specifiers, construction order

## Core ideas
```cpp
class Sensor {
 public:
  virtual ~Sensor() = default;                 // base meant for inheritance -> virtual (or protected) dtor
  const std::string& name() const { return name_; }
 protected:
  Sensor(std::string n, int hz) : name_(std::move(n)), hz_(hz) {}   // only derived can construct
  void tick() { ++frames_; }                   // interface for implementers
 private:
  std::string name_; int hz_; int frames_ = 0; // never visible to derived classes
};

class Lidar : public Sensor {                  // is-a
 public:
  Lidar(std::string n, int rings) : Sensor(std::move(n), 10), rings_(rings) {}  // init base FIRST
  void spin() { tick(); }
 private:
  int rings_;
};
```

### Access: member specifier × inheritance kind
| Base member is | `public` inheritance | `protected` inheritance | `private` inheritance |
|---|---|---|---|
| public | public | protected | private |
| protected | protected | protected | private |
| private | inaccessible | inaccessible | inaccessible |
| `Derived*` → `Base*` for outsiders | ✅ | ❌ | ❌ |

`public` = *is-a* (substitutable). `private` = *implemented-in-terms-of*, usually better written as composition.

### Construction / destruction order
```
construct: virtual bases → direct bases (declaration order) → members (declaration order) → ctor body
destroy:   dtor body → members (reverse) → direct bases (reverse) → virtual bases
```
- A derived constructor that doesn't name the base calls the base's **default** constructor (compile error if there is none).
- If a constructor throws, the already-built members and bases are destroyed, but **its own destructor never runs**.
- Inside base constructors and destructors, the object's dynamic type is the base: virtual calls don't reach the derived class.

### Name hiding and `using`
```cpp
struct Sensor { void configure(int hz); void configure(const std::string& file); };
struct Imu : Sensor {
  using Sensor::configure;                     // without this, the next line HIDES both overloads
  void configure(const std::string& file);
  using Sensor::Sensor;                        // inherit constructors (C++11)
};
std::string Lidar::describe() const { return Sensor::describe() + " rings=16"; }  // call the hidden base version
```

### Diamond & virtual inheritance
```cpp
struct Device { explicit Device(int id); };
struct Powered   : virtual Device { Powered(int id)   : Device(id) {} };
struct Networked : virtual Device { Networked(int id) : Device(id) {} };
struct SmartLidar : Powered, Networked {
  SmartLidar(int id) : Device(id), Powered(id), Networked(id) {}   // MOST-DERIVED builds the virtual base
};
```

## What happens in memory / cost
| Thing | Layout / cost |
|---|---|
| Single non-virtual inheritance | base subobject at offset 0, derived members after it; no overhead |
| `Derived*` → `Base*` (single) | no-op; with multiple inheritance, a pointer **adjustment** for the second base |
| Multiple inheritance | several base subobjects; may need several vptrs |
| Virtual inheritance | shared base reached through a vbase offset (in the vtable): an extra indirection, bigger objects |
| Empty base | Empty Base Optimisation makes it 0 bytes (used by `unique_ptr` deleters, allocators) |

## Pitfalls interviewers ask
1. **Non-virtual public destructor** in a polymorphic base: `delete basePtr` is UB and leaks the derived part.
2. **Name hiding**: a derived overload hides all base overloads with that name.
3. **Forgetting to initialise the base** (or relying on its default constructor).
4. **Calling virtual functions in base constructors/destructors** expecting derived behaviour.
5. **Slicing**: `Sensor s = lidar;` copies only the base part (see M14).
6. **Diamond without `virtual`**: duplicated base, ambiguous member access, double initialisation.
7. **Protected data members**: they leak invariants to every subclass. Prefer private data + protected functions.
8. **Inheriting for code reuse** (`class Path : public std::vector<Pose>`): no virtual dtor, and it leaks the whole interface. Use composition.

## Robotics angle
- Driver layers: `Sensor` → `Lidar`/`Camera`/`Imu` sharing timestamping, frame ids and rate statistics through a protected interface.
- Node and plugin frameworks (ROS `nodelet`, `rclcpp::Node`) are used by inheriting and calling base constructors with configuration.
- Shutdown order matters: motors stop before the power rail drops, so rely on reverse-destruction ordering and RAII members.
- Prefer composition for capabilities (`SmartLidar` has a `PowerRail` and a `NetLink`). Reserve virtual inheritance for genuine shared identity.

## Rapid-fire questions
<details><summary>Show answers</summary>

- *What's the construction order of base, members, and body?* Bases (virtual first), then members in declaration order, then the body. Destruction is the reverse.
- *public vs protected vs private inheritance?* It changes the access of inherited members and whether outsiders can upcast. Only public means is-a.
- *Can a derived class access base private members?* No, never. It only gets protected and public ones.
- *Why make a base constructor protected?* So the base can't be instantiated on its own, only as a subobject.
- *Who initialises a virtual base?* The most-derived class. Intermediate initialisers are ignored.
- *How do you un-hide base overloads?* `using Base::name;` in the derived class.
- *Does a throwing constructor run its destructor?* No. Only fully constructed subobjects are destroyed.
- *When should you use private inheritance over composition?* Rarely: to override a virtual of the base, access protected members, or get the empty base optimisation.
</details>

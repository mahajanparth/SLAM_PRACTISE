# M15 · Object Lifetime: copy/move constructors, Rule of 0/3/5, noexcept

## Core ideas
The six special members, and when each runs:
```cpp
PointBuffer a(100);            // ctor
PointBuffer b = a;             // copy ctor        (init from lvalue)
PointBuffer c = std::move(a);  // move ctor        (init from rvalue)
b = c;                         // copy assignment  (existing object, lvalue)
b = PointBuffer(5);            // move assignment  (existing object, rvalue)
}                              // destructors, reverse order of construction
```

### The rules
| Rule | When | What you write |
|---|---|---|
| **Rule of zero** | members are RAII types (`vector`, `string`, `unique_ptr`) | **nothing**: the compiler gets all five right |
| **Rule of three** (C++98) | you manage a raw resource | dtor + copy ctor + copy assign |
| **Rule of five** | the same, plus you want cheap moves | + move ctor + move assign (`noexcept`) |
| Move-only | unique ownership (handles, `unique_ptr` members) | `= delete` copy, `= default`/write moves |

### What suppresses what (memorise this table)
| You declare… | implicit copy ops | implicit move ops |
|---|---|---|
| nothing | ✅ | ✅ |
| destructor | ✅ (deprecated) | ❌ → "moves" **copy** |
| copy ctor or copy assign | ✅ (the other one) | ❌ → "moves" **copy** |
| move ctor or move assign | ❌ (deleted) | only the one declared |

### Canonical rule-of-five resource class
```cpp
class Buf {
  float* d_ = nullptr; std::size_t n_ = 0;
 public:
  explicit Buf(std::size_t n) : d_(n ? new float[n]{} : nullptr), n_(n) {}
  ~Buf() { delete[] d_; }
  Buf(const Buf& o) : Buf(o.n_) { std::copy(o.d_, o.d_ + n_, d_); }
  Buf& operator=(const Buf& o) { Buf tmp(o); swap(tmp); return *this; }   // copy-and-swap
  Buf(Buf&& o) noexcept : d_(std::exchange(o.d_, nullptr)), n_(std::exchange(o.n_, 0)) {}
  Buf& operator=(Buf&& o) noexcept { Buf tmp(std::move(o)); swap(tmp); return *this; }
  void swap(Buf& o) noexcept { std::swap(d_, o.d_); std::swap(n_, o.n_); }
};
```

### Deep copy of a polymorphic member: `clone()`
```cpp
Keyframe(const Keyframe& o) : cloud_(o.cloud_), desc_(o.desc_ ? o.desc_->clone() : nullptr) {}
Keyframe(Keyframe&&) noexcept = default;              // re-enable moves after writing the copy!
Keyframe& operator=(Keyframe&&) noexcept = default;
```

## What happens in memory / cost
| Operation | `std::vector<Point3>` with 1M points |
|---|---|
| copy | malloc 24 MB + memcpy, ~5–10 ms |
| move | 3 pointer copies + nulling the source, ~ns |
| `vector<T>` growth when T's move is `noexcept` | moves each element |
| … when T's move is **not** `noexcept` (and T is copyable) | **copies** each element (strong guarantee via `move_if_noexcept`) |
| C++17 `T t = make();` (prvalue) | guaranteed elision: no copy, no move |
| `return local;` (NRVO) | usually elided; otherwise an implicit **move** (never write `return std::move(local);`) |

## Pitfalls interviewers ask
1. **Shallow copy of an owning raw pointer** → double free (rule of three violated).
2. **Self-assignment** in a hand-written `operator=` (`delete` first, then read `o`). Use copy-and-swap or an `if (this != &o)` check.
3. **Forgetting `noexcept` on moves**: vectors of your type copy on growth.
4. **Declaring a destructor "for logging"** silently kills moves.
5. **`return std::move(local);`** inhibits NRVO, and `const T local` can't be moved from.
6. **Use after move**: moved-from objects are "valid but unspecified". Only assign to them or destroy them.
7. **Slicing**: copying a `Derived` into a `Base` drops the derived part. Polymorphic deep copy needs `clone()`.
8. **Move ctor that doesn't null the source** → both destructors free the same buffer.

## Robotics angle
- Point clouds and images are big: pass them by `const&`, return by value (elision), `std::move` them into queues and maps.
- `std::vector<Keyframe>`, `std::deque<Scan>`: make sure element types have `noexcept` moves, or growth deep-copies clouds.
- Sensor message types should be **rule of zero** (just `vector`/`string`/`array` members).
- Handles to hardware (CAN socket, camera) are move-only: delete copy, implement moves, own in a `unique_ptr`.
- Loop-closure databases copy keyframes (deep), while the map moves them, so both paths must be deliberate.

## Rapid-fire questions
<details><summary>Show answers</summary>

- *Rule of three/five/zero in one line each?* Three: if you write the dtor, copy ctor, or copy assign, write all three. Five: add the two moves. Zero: use RAII members and write none.
- *Why should moves be `noexcept`?* So containers (via `move_if_noexcept`) use them during reallocation without losing the strong exception guarantee.
- *What does `std::move` do?* Nothing at runtime: it's a cast to an rvalue reference (`T&&`) that makes the move overloads viable.
- *What's copy-and-swap?* Copy into a temporary, then swap with `*this`. It's self-assign safe, gives the strong guarantee, and serves both the copy and move assignment.
- *When is the copy ctor called vs copy assignment?* The ctor initialises a **new** object; assignment overwrites an **existing** one.
- *Does `= default` on a copy ctor keep implicit moves?* No. Any user-declared copy op (even defaulted) suppresses the implicit moves.
- *What's guaranteed copy elision?* C++17: initialising from a prvalue constructs directly in the target, and it works even for non-movable types.
- *State of a moved-from `std::vector`?* Valid but unspecified (empty in practice). Call `clear()` before reusing it if you care.
</details>

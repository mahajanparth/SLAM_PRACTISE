# M18 · Multithreading: thread, mutex, lock_guard, condition_variable, atomics

## Core ideas
```cpp
std::vector<std::thread> workers;
for (int t = 0; t < T; ++t)
  workers.emplace_back([&, t] { partial[t] = work(chunk(t)); });   // capture t BY VALUE
for (auto& w : workers) w.join();                                  // must join (or detach) before destruction

std::mutex m;
{ std::lock_guard<std::mutex> lk(m); shared.push_back(x); }         // RAII lock, released at scope exit
std::scoped_lock lk(m1, m2);                                       // C++17: locks several mutexes without deadlock

std::atomic<int> hits{0};
hits.fetch_add(1, std::memory_order_relaxed);                      // lock-free counter
```

### Blocking queue (producer/consumer) — the interview classic
```cpp
std::optional<T> pop() {
  std::unique_lock<std::mutex> lk(m_);                     // unique_lock: cv needs to unlock/relock
  cv_.wait(lk, [&] { return !q_.empty() || closed_; });    // predicate handles SPURIOUS wakeups
  if (q_.empty()) return std::nullopt;                     // closed and drained
  T v = std::move(q_.front()); q_.pop();
  return v;
}
void push(T v) { { std::lock_guard<std::mutex> lk(m_); q_.push(std::move(v)); } cv_.notify_one(); }
void close()   { { std::lock_guard<std::mutex> lk(m_); closed_ = true; }      cv_.notify_all(); }
```

| Tool | Use for |
|---|---|
| `std::thread` | Run a callable; `join()` waits; destructor of a joinable thread → `std::terminate` |
| `std::mutex` + `lock_guard` | Protect shared data (simple scope) |
| `std::unique_lock` | Movable/unlockable lock; required by `condition_variable::wait` |
| `std::condition_variable` | Sleep until a predicate becomes true (always wait with a predicate) |
| `std::atomic<T>` | Single-variable lock-free updates (counters, flags) |
| `std::async` / `std::future` | Fire-and-get-result tasks (beware `launch::deferred`) |
| `std::shared_mutex` | Many readers / one writer (map queried by planners, updated by mapper) |

## What happens in memory / cost
| Operation | Rough cost |
|---|---|
| Thread creation | ~10–50 µs (→ use a thread pool for small tasks) |
| Uncontended mutex lock/unlock | ~20 ns |
| Contended mutex | µs (syscall, context switch) |
| Atomic increment, uncontended | ~5 ns; contended → cache-line ping-pong |
| **False sharing** | Per-thread counters in the same 64 B cache line thrash; pad with `alignas(64)` or accumulate locally |

## Pitfalls interviewers ask
1. **Data race** = two threads access the same memory, at least one writes, without synchronization → UB (not just "wrong value").
2. `counter++` on a plain `int` is read-modify-write: lost updates. Use `std::atomic` or a mutex.
3. **Deadlock**: two mutexes locked in different orders. Use a fixed order or `std::scoped_lock(a, b)`.
4. **Lost wakeup / spurious wakeup**: always `wait(lk, predicate)`; modify the predicate state *under the mutex*.
5. Capturing loop variables by reference in a thread lambda (`[&]` with `t`) → all threads see the final `t`.
6. Forgetting `join()` → `std::terminate`. Exceptions between `thread` creation and `join` → use RAII (`std::jthread` in C++20).
7. Returning references to queue internals from a locked function: the lock is released, the reference escapes.
8. `std::thread(f, ref)` copies arguments; use `std::ref(x)` to pass by reference.
9. `volatile` is **not** a synchronization primitive in C++.
10. Holding a lock while doing slow work (I/O, `notify` is fine either way, but keep critical sections short).

## Robotics angle
- **Sensor driver → processing**: lidar/IMU callbacks push into a bounded thread-safe queue; the estimator thread pops.
- **Front-end / back-end split**: tracking at camera rate, mapping/loop closure on another thread (ORB-SLAM's three threads).
- **Data parallel over point clouds**: split into chunks, reduce per-thread partials, then combine (no shared writes in the hot loop).
- **Shutdown**: every blocking wait needs a way to be woken (a `close()` flag) or the node hangs on Ctrl-C.
- Real-time loops avoid locks that can block for long; use lock-free SPSC ring buffers or try-lock + drop.

## Rapid-fire questions
<details><summary>Show answers</summary>

- *mutex vs atomic?* Atomic for a single variable with simple ops; mutex to keep an invariant across several variables.
- *lock_guard vs unique_lock?* lock_guard: fixed scope, cheapest. unique_lock: can unlock/relock/move, needed for condition variables.
- *Why does `cv.wait` take a predicate?* Spurious wakeups, and the condition may already be true (no lost wakeup).
- *What is false sharing?* Independent variables on the same cache line written by different cores, which bounces the line.
- *How do you avoid deadlock?* Global lock order, `std::scoped_lock`, never call unknown code while holding a lock.
- *notify_one vs notify_all?* One waiter can make progress per item → notify_one. State change everyone must see (shutdown) → notify_all.
- *Is `std::shared_ptr` thread-safe?* The control block refcount is; the pointed-to object and the same shared_ptr instance are not.
- *What does `memory_order_relaxed` guarantee?* Atomicity only, no ordering. Fine for counters, not for publishing data.
</details>

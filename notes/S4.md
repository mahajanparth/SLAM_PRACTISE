# S4 · Point Cloud Basics: voxels, kNN, normals, outliers, range images

## Core ideas
### Voxel grid
```cpp
struct Key { long long x, y, z; bool operator==(const Key& o) const { return x==o.x && y==o.y && z==o.z; } };
struct KeyHash { size_t operator()(const Key& k) const {
  return size_t(k.x * 73856093LL ^ k.y * 19349663LL ^ k.z * 83492791LL); } };
Key key{(long long)std::floor(p.x() / leaf), ...};      // floor, NOT (int) cast: -0.3 -> -1, not 0
std::unordered_map<Key, std::pair<Eigen::Vector3d, int>, KeyHash> acc;  acc.reserve(n);
```
Sort-based alternative: compute keys, `std::sort` by key, then run-length reduce. Deterministic output order, cache friendly, O(N log N).

### kNN (brute force)
Squared distances, then `std::partial_sort` (O(N log k)) or a max-heap of size k (`std::priority_queue`), or `std::nth_element` + sort the first k (O(N + k log k)). Clamp k to N.

### Normals via PCA
$$\bar{\mathbf p}=\tfrac1k\sum\mathbf p_i,\qquad C=\tfrac1k\sum(\mathbf p_i-\bar{\mathbf p})(\mathbf p_i-\bar{\mathbf p})^T,\qquad C\mathbf v_j=\lambda_j\mathbf v_j,\ \lambda_0\le\lambda_1\le\lambda_2$$
Normal is $\mathbf v_0$ (smallest eigenvalue). Orient it so that $\mathbf n\cdot(\mathbf o_{\text{sensor}}-\mathbf p)\ge0$.
Surface variation (curvature) $=\lambda_0/(\lambda_0+\lambda_1+\lambda_2)$. LOAM-style features: linearity $(\lambda_2-\lambda_1)/\lambda_2$, planarity $(\lambda_1-\lambda_0)/\lambda_2$.
```cpp
Eigen::SelfAdjointEigenSolver<Eigen::Matrix3d> es(C);   // eigenvalues ASCENDING
Eigen::Vector3d n = es.eigenvectors().col(0);
```
**Two-pass** covariance: subtract the centroid first. One-pass $E[pp^T]-\bar p\bar p^T$ cancels catastrophically far from the origin (UTM coordinates!).

### Statistical outlier removal (SOR)
$\bar d_i$ = mean distance from point i to its k nearest neighbours. Keep the point if $\bar d_i\le\mu+\alpha\sigma$, where $\mu,\sigma$ are taken over all $\bar d_i$.
Radius outlier removal (ROR): keep the point if it has ≥ m neighbours within radius r.

### Range image (spinning lidar)
$$\text{az}=\operatorname{atan2}(y,x),\qquad \text{el}=\operatorname{atan2}\!\big(z,\sqrt{x^2+y^2}\big)$$
$$\text{col}=\Big\lfloor\tfrac{\text{az}+\pi}{2\pi}W\Big\rfloor,\qquad \text{row}=\Big\lfloor\tfrac{\text{fov}_{up}-\text{el}}{\text{fov}_{up}-\text{fov}_{down}}H\Big\rfloor$$
Bounds-check, and keep the nearest point per pixel (occlusion).

### Ground removal
Naive: `z < -sensor_height + thr`. This fails on slopes, ramps, and when the vehicle pitches. Better: per-XY-cell min-z, RANSAC plane (S5), concentric zones with local planes (Patchwork), or a ring-based slope test on the range image.

## What happens in memory / cost table
| Container | 1M points | Note |
|---|---|---|
| `std::vector<Eigen::Vector3d>` | 24 MB | not vectorizable, no alignment issue |
| `std::vector<Eigen::Vector3f>` | 12 MB | |
| `std::vector<Eigen::Vector4f>` | 16 MB | padded for SSE, 16-B aligned |
| `Eigen::Matrix3Xf` | 12 MB contiguous | GEMM-friendly |
| `unordered_map` voxel entry | ~50–80 B + node malloc | reserve; or a sort-based approach |

| Algorithm | Cost |
|---|---|
| Voxel (hash) | O(N) expected |
| Voxel (sort) | O(N log N) |
| Brute kNN, one query | O(N log k) |
| Normals with brute kNN | O(N² log k), so you need a KD-tree (S5) or voxel hashing |
| Range image | O(N), and gives O(1) neighbour lookup |

## Pitfalls interviewers ask
1. `(int)(p.x/leaf)` truncates toward zero: −0.01 and +0.01 land in the same voxel. Use `std::floor`.
2. A weak hash (e.g. `x ^ y ^ z`) causes huge collision chains on symmetric keys.
3. `sqrt` inside the kNN comparison: wasted work. Compare squared distances.
4. k > N, k ≤ 0, empty cloud, duplicate points (ties): define the behaviour.
5. Normals: forgetting the orientation; using `col(2)` (the largest eigenvalue); fewer than 3 neighbours; collinear neighbours (λ1 ≈ 0, so the normal is undefined).
6. SOR with σ = 0 (all points identical): don't divide by σ, use ≤.
7. Range image: `atan2` range edge (az = π → col = W), out-of-FOV rows, and returns at range 0.

## Robotics angle
- Voxelize before ICP for uniform density (near points would otherwise dominate), fewer points, and faster NN.
- Organized clouds (range images, depth images) give pixel neighbours for free. Unorganized clouds need a KD-tree or voxel hash.
- Normals feed point-to-plane ICP, ground segmentation and plane landmarks.
- SOR removes isolated returns (dust, rain, multipath). ROR is cheaper with a radius search.
- Incremental voxel maps (iVox, ikd-tree) are what fast LIO systems (FAST-LIO2) use.

## Rapid-fire questions
<details><summary>Show answers</summary>

- *Why voxelize before ICP?* Uniform density, fewer points, and less bias toward near-range points.
- *Organized vs unorganized cloud?* Organized has a 2D grid structure (H×W, e.g. a range or depth image) with implicit neighbours. Unorganized is a plain list.
- *Why squared distances?* Monotonic, so ordering is preserved, and you skip the sqrt.
- *Memory of 1M `Vector3d` vs `Vector3f`?* 24 MB vs 12 MB. `Vector4f` is 16 MB, padded for SIMD.
- *Which eigenvector is the normal?* The one for the smallest eigenvalue. `SelfAdjointEigenSolver` sorts ascending, so it's `col(0)`.
- *How do you orient a normal?* Flip it if $\mathbf n\cdot(\text{viewpoint}-\mathbf p)<0$.
- *Hash map vs sort for a voxel grid?* Hash is O(N) but random-access and non-deterministic order. Sort is O(N log N), cache friendly and deterministic.
- *Why does z-threshold ground removal fail?* Slopes, curbs, ramps, and vehicle pitch/roll.
</details>
